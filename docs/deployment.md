# Выбор способа развёртывания

Оба варианта используют корневой Dockerfile .NET 10 и внешнюю PostgreSQL. Это альтернативные схемы, а не последовательные этапы.

| Вариант | Что настраивает оператор | Руководство |
| --- | --- | --- |
| VPS + GitHub Actions | Linux, Docker/Compose, SSH, домен, Caddy, постоянные каталоги, резервные копии | [VPS](vps-deployment.md) |
| Timeweb App Platform | Docker-сборка, runtime-переменные, БД, домен/TLS, постоянное хранилище средствами платформы | [App Platform](timeweb-deployment.md) |

## Общие условия

1. Отдельно подготовить PostgreSQL и сетевой доступ к ней.
2. Задать production-секреты через runtime, не через Docker build args.
3. Обеспечить постоянный `uploads` и резервное копирование БД/файлов.
4. Применить миграции командой `--migrate-only` до запуска обновлённого API.
5. Проверить `/server/ready`, авторизацию, сообщения, старые/новые вложения и SignalR по внешнему HTTPS.
6. Включить Firebase только с правильными credentials и проверить устройство отдельно.

Нормальный запуск API не мигрирует БД. Образ может успешно собраться и при этом не стартовать из-за отсутствующей runtime-конфигурации. Готовность процесса не доказывает работоспособность Firebase.

## Что делает workflow

Push в `master` и PR запускают тесты. Публикация образа/деплой включаются только при `VPS_DEPLOY_ENABLED=true`; PR не публикует production. Включённый VPS workflow собирает GHCR-образ, запускает миграции и обновляет контейнеры с проверкой ready. Проверка переменной в файле workflow не подтверждает, что она включена в вашем GitHub.

После применения миграции возврат к старому образу безопасен только при совместимой схеме. [Обновления и восстановление](operations.md).
