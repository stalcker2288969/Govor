# E2EE v1

Новые личные сообщения и сообщения приватных групп/каналов требуют E2EE.
Сервер проверяет подпись и права доступа, сохраняет и пересылает зашифрованный
конверт. Он не получает приватные ключи устройств или ключи файлов.
Новый мобильный клиент шифрует сообщения всех чатов, включая публичные группы;
сервер сохраняет совместимость с открытыми сообщениями публичных групп.

## Протокол

Используется `jose-jwt` 5.3.0: JWE JSON Serialization (RFC 7516),
RSA-OAEP-256 с RSA 3072 для передачи ключа каждому устройству, AES-256-GCM для
содержимого и JWS ES256 (RFC 7515) для подписи полного конверта.
Алгоритмы фиксированы; сжатие, незашифрованный режим и выбор алгоритма сервером
не поддерживаются. Это прикладной протокол на JOSE, а не Signal/MLS.

Поле `EncryptedContent` содержит `govor.e2ee.v1:` и компактный JWS. В подписанном
конверте находятся версия, ID сообщения и чата, тип чата, публичный ключ автора,
ID сессии, ссылка на ответ, время, признак редактирования, отпечатки устройств,
ID вложений и JWE. Текст и секреты вложений находятся только внутри JWE.
Публичный ключ RSA подписан ключом ES256 с отдельным контекстом
`govor-key-binding-v1`. Отпечаток SHA-256 связывает оба публичных ключа.

Код `Govor.Application/E2ee/E2eeProtocol.cs` и его копия в мобильном репозитории
`Govor.Mobile/Services/E2ee/E2eeProtocol.cs` должны оставаться идентичными.
Изменение формата требует новой версии протокола и совместимых клиентов.

## Устройства и доверие

Клиент генерирует отдельную пару ключей шифрования/подписи для каждой сессии.
Приватные ключи хранятся только в MAUI SecureStorage, раздельно для сервера,
аккаунта и сессии. Ключи предыдущих сессий остаются локально для чтения истории.
Ошибка записи или регистрации останавливает отправку; отката к открытому тексту нет.

Каждый новый отпечаток нужно сверить лично или по независимому доверенному
каналу. Приложение показывает свой отпечаток и отпечаток другого устройства.
Простое нажатие подтверждения без сверки не защищает от подстановки устройства
скомпрометированным сервером. Дополнительно подтверждается состав получателей
каждого чата при первом использовании и изменении списка устройств/участников.
Эти подтверждения хранятся локально, а не на сервере.

Это не система прозрачности ключей и не подписанный участниками протокол
управления составом групп. Сервер остаётся источником списка участников и
статуса сессий. Если он скрывает изменения/отзыв устройств, это невозможно
независимо обнаружить без дополнительного протокола. Не следует заявлять
защиту уровня Signal/MLS или защиту от любых действий злонамеренного сервера.
До публичного релиза требуется независимый аудит протокола и интеграции.

## Серверные API

- `PUT /api/e2ee/device`: публичный `DeviceKey` текущего пользователя/сессии.
  Повторная регистрация тех же ключей допустима; смена ключей внутри сессии
  запрещена. Истёкшая или отозванная сессия не может регистрировать ключи.
- `GET /api/e2ee/conversations/{type}/{conversationId}/keys`: список участников
  и зарегистрированных устройств; `type=0` — личный чат, `type=1` — группа.
  Требуется доступ к чату. Возвращаются только публичные данные.
- SignalR `Send`/`Edit` и HTTP загрузки истории сохраняют существующие поля DTO.
  `MessageEditResponse` дополнительно возвращает `ReplyToMessageId` для проверки
  подписанного контекста редактирования.

Для офлайн-доставки устройства с истёкшей, но не отозванной сессией остаются
получателями. Отозванные сессии исключаются. При изменении набора устройств
необходимо заново получить ключи, подтвердить состав и перешифровать сообщение.
В группах это проверяется под существующей блокировкой модерации, чтобы бан
не мог гоняться с сохранением сообщения. Каждый отправляемый конверт получает
новый случайный ключ содержимого. Исключённый участник сохраняет доступ к уже
полученным сообщениям, но его ключ больше не включается в новые конверты.

ID сообщения генерируется клиентом и подписывается. Повторная отправка того же
конверта не создаёт второй записи/задания push. Редактирование проверяет ID,
автора, чат, ответ, вложения и время версии. Клиент хранит принятые версии,
отклоняет откат к старой версии и проверяет подпись перед показом текста.

## Вложения

Клиент шифрует файл AES-256-GCM с новым случайным 32-байтовым ключом и 12-байтовым
nonce. Формат: `nonce || ciphertext || tag(16)`; AAD — `govor-attachment-v1`.
Сервер получает случайное имя `.bin`, тип `application/vnd.govor.encrypted` и
байты шифротекста. Исходное имя, MIME-тип и ключ передаются только внутри
зашифрованного сообщения. Поле `EncryptedKey` загрузки должно быть пустым.
Незашифрованные загрузки типа Message отклоняются; аватары остаются открытыми.

Получатель сначала проверяет и расшифровывает сообщение, сохраняет секреты
вложений локально, затем загружает и проверяет файл. Предельный размер исходного
файла — 19 MB, текста — 20 000 символов, устройств — 500, конверта — 1 000 000
символов. Ограничения предотвращают неограниченный рост RSA-конверта.

## Обновление и ограничения

1. Собрать и согласованно обновить сервер и клиенты всех участников. Старые
   клиенты не смогут отправлять сообщения в защищаемые чаты. Автоматического
   временного перехода на открытый текст нет.
2. Пользователям нужно войти в новый клиент для регистрации устройств. Пока
   хотя бы у одного участника нет ключа, новый клиент блокирует отправку.
3. Сверить отпечатки и состав получателей. Проверить личный чат, приватную
   группу/канал, редактирование, вложения, новое устройство и исключение участника
   на реальных устройствах перед развёртыванием.

Новая миграция БД не требуется: используются существующие таблицы CryptoSession
и SignedPreKey, в которых хранятся только публичные данные. Старые заготовки
Signal prekeys не превращаются автоматически в совместимые ключи JOSE; если
они уже были привязаны к сессии, нужна новая сессия.

Уже сохранённая открытая история и старые файлы не становятся секретными задним
числом. Они не удаляются; клиент помечает открытую историю `[Без E2EE]`.
При невозможности расшифровки показывается статус без шифротекста и вложений;
неуспешный результат не сохраняется вместо исходной записи локального кэша.

Новый физический аппарат не получает прошлые ключи автоматически. После удаления
SecureStorage или потери устройства зашифрованная история без другого устройства
с нужными ключами недоступна. Серверного восстановления/экспорта ключей нет.
Локальный кэш сообщений пока хранит уже расшифрованный текст, как и раньше.

В v1 нет forward secrecy/post-compromise security и Double Ratchet/MLS:
компрометация приватного ключа устройства позволяет расшифровать сохранённые
сообщения, адресованные этому ключу. Отзыв сессии исключает её из будущих
получателей; украденные ключи и уже прочитанные сообщения отозвать невозможно.
Метаданные, участники, размеры и время сообщений видны серверу. Скомпрометированное
устройство участника и копирование текста самим участником за пределами модели
защиты. HTTPS по-прежнему требуется для авторизации и защиты транспорта.

## Проверка

```powershell
dotnet test Govor.Server.Tests/Govor.Server.Tests.csproj
# В мобильном репозитории:
dotnet test Govor.Mobile.Tests/Govor.Mobile.Tests.csproj
dotnet build Govor.Mobile/Govor.Mobile.csproj -f net10.0-android -p:TargetFrameworks=net10.0-android
```

Тесты проверяют совместимость шифрования/расшифровки, подписи и контекст,
доступ посторонних, отзыв устройств, смену состава группы, версии сообщений,
секреты вложений, отказ сверки ключей и отказ записи приватного ключа.
