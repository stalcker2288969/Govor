# Диагностика и порядок исправлений

## Основание и пределы проверки

Проверен master Govor-team/Govor, commit 4603be9f714135e0af72d505d17f3d1709834bea (GitHub и локальный checkout совпали). Изучены контроллеры, хабы, сервисы, DTO, EF-модели, DI, запуск и часть MAUI-интеграции. Старый опубликованный GitBook оставался на ревизии 18.12.2025 и расходился с кодом.

При исходной диагностике сборка API на SDK 10.0.400 прошла с 90 предупреждениями, но тесты .NET 8 не восстанавливались из-за NU1201. Обновление 24.10.2026: серверные тесты перенесены в `tests`, обновлены до .NET 10; Release-сборка и 710 тестов проходят на SQLite и изолированной PostgreSQL. Покрытие Application: 98,88% строк и 93,53% ветвей. Инструкции и ограничения проверки — в [tests/README.md](../tests/README.md). Production, Firebase и UI на устройствах не проверялись.

Ниже «подтверждено» означает выявлено по конкретному коду или диагностике сборки, а не воспроизведено атакой на живой сервис.

## P2 — надёжность и сопровождение

- Конкурентные регистрации могут превысить лимит приглашения; IsActive не проверяется. Нужна атомарная квота.
- Повторный Read конфликтует при гонке по unique(MessageId, UserId); требуется идемпотентная запись.
- Нет clientMessageId/outbox: после сохранения уведомление может упасть, а повторная отправка создаст дубль.
- Пагинация только по SentAt пропускает одинаковые timestamps; нужен стабильный курсор.
- Состояние соединений локально процессу; для нескольких инстансов требуется общее решение.
- CORS принимает любой origin с credentials; sensitive EF logging включён без ограничения окружения.
- Firebase обязателен даже для локального старта; внешние зависимости должны включаться явно.
- global.json содержит некорректную sdk/version; solution зависит от внешнего SmartRes, а API — от DLL в libs.
- Дубликат маппинга UserProfileDto, nullable выключен в API, а предупреждения CS0649 уже указывают реальные дефекты.
- Приглашение определяет роль одновременно с отдельной таблицей Admin; выбрать один источник.
- PrivacyUserSettings и Blocked-модель не означают, что приватность и блокировка покрывают все сценарии.

NuGet сообщил NU1903 для AutoMapper 16.0.0. [GHSA-rvv3-g6hj-g44x](https://github.com/advisories/GHSA-rvv3-g6hj-g44x) описывает DoS от рекурсивного mapping; исправленная версия ветки 16 — 16.1.1. Это подтверждение уязвимости зависимости; доступность конкретного exploit-пути в Govor отдельно не доказана.

## MAUI и стеклянный интерфейс

MessagesListController присваивает EncryptedContent = text; mapping читает его прямо в Text, а репозиторий редактирует как NewEncryptedContent = newText. Следовательно, в проверенном пути сообщения передаются обычным текстом. Хранение ключей на сервере не делает этот путь E2EE.

ChatHub клиента отбрасывает сообщения с пустым текстом, даже если есть вложение. Клиент подписан на MessageSent, которое сервер не отправляет. Перезапуск из Closed может конфликтовать с logout; refresh на любом HTTP-сбое очищает токены. MessagesListController.SendAsync возвращает Success(true), не проверяя результат SendMessageAsync; экран может считать неуспешную отправку успешной. Эти проблемы важнее полировки оформления.

В ChatPage.xaml есть слои с Opacity и Shadow. Визуально подтвердить эффект, FPS и поведение blur без запуска приложения нельзя. Рекомендуется отдельно измерить скролл длинного чата, работу клавиатуры, контраст текста на светлом/тёмном фоне и отключение тяжёлых эффектов. Полный UI-аудит не проводился.

## Последовательность работ

1. Закрыть P0, добавить проверки «пользователь C не может читать/писать/читать ключи чата A–B; User не управляет Admin».
2. Выровнять .NET и тесты; проверить реальные PostgreSQL-запросы и DI через старт приложения.
3. Исправить P1: события двух участников, HideForMe, медиа, ключи, logout.
4. Закрепить API контрактами и интеграционными тестами HTTP/SignalR, включая повторные и параллельные операции.
5. Решить E2EE и доставку; после этого расширять группы и оптимизировать визуальные эффекты.

Критерий готовности: воспроизводимый запуск, зелёные проверки доступа, согласованный MAUI-контракт и отсутствие известных неработающих методов. Архитектурная переработка должна опираться на эти проверки, а не начинаться с переписывания всего приложения.
