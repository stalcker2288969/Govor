# Аутентификация

## Последовательность

1. Новый клиент регистрирует SRP-параметры через `POST /api/auth/register`. Для входа использует `POST /api/auth/password/challenge`, затем `/password/login` с доказательством.
2. Проверяет серверное доказательство и сохраняет пару access/refresh. Точный формат — [регистрация и вход](authcontroller.md).
3. HTTP передаёт `Authorization: Bearer <accessToken>`. Для SignalR задаётся `AccessTokenProvider`; query `access_token` принимается только на путях `/hubs`.
4. [Refresh](refreshcontroller.md) последовательно заменяет оба токена. [Сессии](../sessioncontroller.md) позволяют отозвать отдельное устройство или все сеансы.
5. [Восстановление](../../password-recovery.md) открывает зашифрованный архив истории. Успешный вход и наличие ключей старой истории — разные состояния.

## Токены и отзыв

Access JWT содержит `userId`, `sid`, `tokenType: access` и роль `User`/`Admin`. Подпись HS256 и срок проверяются; issuer/audience не проверяются. JSON-ответы не устанавливают HttpOnly-cookie. Значения по умолчанию: access 10 минут, refresh-сессия 30 дней.

Bearer middleware проверяет по БД владельца `sid`, срок и отсутствие отзыва. Refresh JWT не принимается как access. SignalR-фильтр заново проверяет сессию при каждой команде и прерывает соединение при отказе. Отзыв не следует трактовать как гарантированное мгновенное физическое закрытие всех соединений: у разных хабов разная маршрутизация событий. ChatsHub направляет события активным сессиям.

Refresh содержит случайный `jti`; замена хеша выполняется условным атомарным обновлением. Из двух конкурирующих запросов со старым refresh только один может заменить хеш. Это не долговременный журнал replay и не отзыв всей семьи токенов.

## Старые аккаунты

`POST /api/auth/login` с открытым паролем оставлен для bcrypt-аккаунтов. После настройки SRP он возвращает `401 Auth.PasswordProofRequired`. Новый клиент не должен автоматически откатываться на старый вход; [процедура перехода](../../password-recovery.md) требует явной смены пароля.

## Ограничения и хранение

Регистрация, старый login, SRP challenge/login и challenge/authorize действий имеют общий лимит `30 запросов/минуту` на `RemoteIpAddress`, без очереди; превышение — `429`. Challenge одноразовый и действует две минуты. Хранилище challenge находится в памяти процесса, поэтому несколько инстансов требуют отдельной схемы маршрутизации/общего хранилища.

На клиенте храните секреты в защищённом хранилище, сериализуйте refresh и сохраняйте новую пару до следующего запроса. Временная сеть/`5xx` не означает необходимость стирать ключи истории. На внешней сети обязателен HTTPS; [параметры proxy](../../configuration.md).
