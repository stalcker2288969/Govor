# Вход по паролю и восстановление E2EE

## Пользовательские сценарии

Регистрация остаётся на экране регистрации и использует единственный
`POST /api/auth/register` в `AuthController`. Отдельного контроллера регистрации нет.
Новый клиент передаёт SRP salt/identity/verifier вместо открытого пароля.
Существующие проверки имени, приглашения и обязательного канала сохранены.

После настройки парольной копии ключа обычный вход на новом устройстве восстанавливает
зашифрованный архив истории автоматически. Пароль не хранится и не передаётся серверу
новым методом входа. Локально в SecureStorage сохраняется производный ключ архива.
Резервный код остаётся дополнительным способом переноса и восстановления.

В настройках доступны:

- **Сменить пароль с сохранением истории**: подтверждение прежнего пароля, новый
  пароль с повтором, перешифрование копии кода; ключ аккаунта и история сохраняются.
  Другие сессии и их push-токены отзываются.
- **Начать общение с новыми ключами**: подтверждение потери истории и текущего пароля;
  создаются новый ключ аккаунта, код и ключи устройства, другие сессии отзываются.
  Собеседник получает уведомление при первой обработке нового ключа. Сверять ключи
  вручную не нужно. Необъявленная подмена закреплённого ключа по-прежнему блокируется.

Если забыт пароль, администратор может сбросить доступ к аккаунту, но этим не
расшифровывает старую историю. После входа с выданным паролем пользователь задаёт
новый пароль и восстанавливает прежний архив резервным кодом/с доверенного устройства.
Без прежнего пароля, кода и доступного устройства старую историю восстановить нельзя;
можно явно начать общение с новыми ключами. Уже полученная собеседниками история
современных сертифицированных сообщений у них сохраняется.

## Переход со старого входа

Старый bcrypt-аккаунт один раз требует выбрать **другой** пароль. Только в этой
явной процедуре старый пароль проверяется прежним серверным методом; новый пароль
в сеть не отправляется. Сервер проверяет различие паролей, а не только UI.
Если на сервере уже был архив без парольной копии, для первого восстановления
всё ещё нужен прежний код либо устройство с ключами. Неизвестные секреты сервер
не может создать задним числом. Старая refresh-сессия без нового входа также не
имеет производного парольного ключа.

Клиент запоминает успешный SRP-вход для адреса сервера и имени. Если сервер позже
предлагает старый вход, автоматической отправки пароля не происходит. На экране
появляется действие «Продолжить после сброса пароля» только после такой ошибки.
Обычная ссылка «Зарегистрируйтесь!» остаётся на месте. Первый вход с чистого
устройства всё ещё доверяет настоящему серверу и HTTPS, включая предложение миграции.

## Протокол и хранение

Используется SRP-6a из `srp` 1.0.7 / srp.net, группа 4096 бит и SHA-512.
Это не OPAQUE и не независимо проверенная реализация всего прикладного протокола.
PBKDF2-SHA256 (600 000 итераций, случайная соль 32 байта) и отдельные контексты
HKDF-SHA256 дают секрет аутентификации и ключ парольной копии. Они не совпадают;
восстановление не использует общий сеансовый SRP-ключ.

Случайный резервный код шифрует основной архив. Парольный ключ шифрует копию кода
в JWE dir/A256GCM. Подпись ключа аккаунта связывает её с владельцем, текущими SRP
параметрами и версией учётных данных. Изменение пароля атомарно меняет verifier
и эту копию. Сброс забытого пароля очищает парольную копию, сохраняя основной архив.
В БД нет открытого пароля, кода или приватного ключа аккаунта. Однако кража БД
позволяет подбирать слабые пароли офлайн; восстановление по паролю зависит от
его стойкости. Получив пароль и архив, атакующий получает доступ к истории.

Challenge и подтверждения действий одноразовые, действуют две минуты; подтверждения
смены пароля/сброса связаны с пользователем, сессией и назначением. Изменение версии
учётных данных инвалидирует начатые доказательства. На клиенте журналы смены пароля
и сброса ключей позволяют проверить серверный результат после потери ответа до
замены локальных секретов. Старый пароль при нормальном входе не отправляется.

Замена ключа аккаунта публикуется в журнале `E2eeIdentityChanges` с последовательным
epoch. Журнал доступен самому аккаунту и собеседникам с доступом к переписке;
участник группы может проверить автора сохранённых сообщений после его выхода.
Сервер авторизует сброс по свежему доказательству пароля, а не по подписи утраченного
ключа. Это явная часть доверия серверу, не криптографическое доказательство
непрерывности старого ключа. Исторические сертифицированные сообщения до сброса
принимаются без отката текущего закреплённого ключа.

Публичный сертификат прежнего ключа текущей сессии сохраняется отдельно в журнале
сброса: он нужен для проверки v1-сообщений, в которых ещё нет сертификата внутри.
Запрос исторического автора принимает `identityKey` и проверяет доступ к чату;
архивный сертификат не становится получателем новых сообщений и не возобновляет сессию.

Хранилище challenge пока находится в памяти процесса (лимит 1024). Для нескольких
экземпляров нужны маршрутизация всего обмена на один экземпляр либо распределённое
одноразовое хранилище. Лимит регистрации, входа и доказательств действий —
30 запросов/минуту на RemoteIpAddress; фоновое чтение парольной копии в него не входит.
За reverse proxy необходимо настроить доверенные forwarded headers и подходящие
лимиты. HTTPS обязателен. Криптографический аудит и нагрузочная проверка нужны
перед публичным выпуском. Ограничения FS/PCS и доверия группам из [e2ee.md](e2ee.md)
сохраняются; парольное восстановление их не устраняет.

## API

Все маршруты находятся в `AuthController`. Регистрация и challenge/login анонимные;
остальные требуют access token и определяют владельца из JWT.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| POST | /api/auth/register | Единая регистрация: SRP либо совместимый старый формат |
| POST | /api/auth/password/challenge | Начать вход |
| POST | /api/auth/password/login | Проверить доказательство; токены и серверное доказательство |
| GET | /api/auth/password | Собственные параметры и зашифрованная копия кода |
| PUT | /api/auth/password/enrollment | Однократное обновление старого входа |
| PUT | /api/auth/password/recovery | Создать подписанную парольную копию кода |
| POST | /api/auth/password/{change\|reset}/challenge | Начать подтверждение действия |
| POST | /api/auth/password/{change\|reset}/authorize | Получить одноразовое разрешение |
| POST | /api/auth/password/change | Атомарная смена пароля с сохранением архива |
| POST | /api/auth/password/reset-encryption | Явный сброс ключей, новый архив и запись журнала |
| GET | /api/e2ee/identities/{userId}/changes | История смены ключа доступного собеседника |

## Локальная проверка

Из корня серверного репозитория, с запущенной отдельной локальной PostgreSQL
и созданной БД `govor_dev` (подставьте собственные реквизиты):

```powershell
$env:ASPNETCORE_ENVIRONMENT = 'Development'
$env:ConnectionStrings__GovorDbContext = 'Host=127.0.0.1;Port=5432;Database=govor_dev;Username=postgres;Password=YOUR_LOCAL_PASSWORD'
$env:Firebase__Enabled = 'false'
dotnet restore Govor.API/Govor.API.csproj
dotnet run --project Govor.API/Govor.API.csproj --no-launch-profile -- --migrate-only
dotnet run --project Govor.API/Govor.API.csproj --launch-profile http
```

Первый `run` применяет все миграции и завершается; второй запускает API на
`http://localhost:7155`. HTTP предназначен для локальной проверки. Для проверки
на устройстве настройте доступный устройству адрес и HTTPS.
Новые миграции — `20261024105815_PasswordBasedRecovery` и
`20261024114709_PreserveResetSigners`, после `20261024084524_E2eeRecoveryAndRotation`.
Пользовательская БД агентом не обновлялась.

Проверить регистрацию, повторный вход с чистым SecureStorage без ввода кода,
смену пароля и вход новым паролем, восстановление кодом после административного
сброса, явный сброс ключей и уведомление на втором аккаунте. Отдельно проверить
потерю ответа при смене пароля/сбросе и повторный запуск клиента.

```powershell
dotnet test Govor.Server.slnx
# Из корня мобильного репозитория:
dotnet test Govor.Mobile.Tests/Govor.Mobile.Tests.csproj
dotnet build Govor.Mobile/Govor.Mobile.csproj -f net10.0-android -p:TargetFrameworks=net10.0-android
```

Общие `PasswordProtocol` и `E2eeRecoveryProtocol` в двух репозиториях должны
совпадать за исключением namespace. Источники SRP:
[srp.net](https://github.com/secure-remote-password/srp.net),
[пакет srp](https://www.nuget.org/packages/srp/1.0.7).
